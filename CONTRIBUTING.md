# Contributing to tidy_imports

Thank you for your interest in contributing!

## Development Setup

```sh
# Clone the repository
git clone https://github.com/Franklyn-R-Silva/tidy_imports.git
cd tidy_imports

# Install dependencies
dart pub get

# Run tests
dart test

# Run the tool locally (from a Dart project)
dart run bin/tidy_imports.dart
```

## Running Quality Checks

```sh
dart analyze          # static analysis
dart format .         # auto-format
dart test             # test suite
```

All three must pass with no issues before a PR will be merged.

## Commit Message Format

This project uses **Conventional Commits** because
[Release Please](https://github.com/googleapis/release-please) reads them
to decide the version bump automatically.

| Prefix | When to use | Version effect |
|---|---|---|
| `feat: ...` | New feature | minor bump |
| `fix: ...` | Bug fix | patch bump |
| `feat!: ...` | Breaking change | major bump |
| `docs: ...` | Documentation only | no bump |
| `test: ...` | Adding/fixing tests | no bump |
| `refactor: ...` | Refactor without behavior change | no bump |
| `chore: ...` | Maintenance, CI, tooling | no bump |

Examples:

```
feat: add --dry-run flag to preview changes without writing
fix: handle files with only a BOM character correctly
docs: add example of Flutter pre-commit hook setup
feat!: rename --no-comments to --skip-comments
```

For breaking changes you can also use the `BREAKING CHANGE:` footer:

```
feat: change default sort order

BREAKING CHANGE: relative imports now appear before package imports
```

## Release Process

Releases are **fully automated**. You do not need to edit version numbers or
create git tags manually.

1. Commit to `main` using Conventional Commits.
2. The **Release Please** GitHub Action opens/updates a "Release PR" that bumps
   `pubspec.yaml`, `lib/src/version.dart`, and `CHANGELOG.md`.
3. When ready to release, **merge the Release PR**.
4. The action automatically creates the `vX.Y.Z` tag and GitHub Release.
5. After the release, publish to pub.dev:

```sh
dart pub publish
```

## Generating Build Metadata

To embed git metadata in the CLI `--version` output during development:

```sh
dart run tool/gen_version.dart
```

This generates `lib/src/build_info.dart` (gitignored). The CLI picks it up
automatically if present.

## Project Structure

```
bin/
  tidy_imports.dart   # CLI entry point
lib/
  tidy_imports.dart   # Public library export (required by pub.dev)
  sort.dart           # Core import-sorting logic
  files.dart          # File discovery
  args.dart           # Help output
  src/
    version.dart      # Version constant (updated by Release Please)
    build_info.dart   # Git metadata (gitignored, generated by tool/)
test/
  sort_test.dart      # Test suite
tool/
  gen_version.dart    # Generates build_info.dart
```

## Opening a Pull Request

1. Fork the repository and create a branch from `main`.
2. Make your changes following the coding style in the existing files.
3. Add or update tests in `test/sort_test.dart`.
4. Open a PR with a clear description of what changed and why.
